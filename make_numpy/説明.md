# make_numpy の説明

> この配布版では `settings.py` の既定を「白板補正なし・黒補正なし・再構成しない（`RECONSTRUCT_MISSING = False`）」にしてある。
> 使い方はリポジトリ直下の `README.md` を先に読む（再構成するときの準備も README の「再構成」）。以下は元のプロジェクトでの詳しい説明
> （`main.py` / `automation_rgb.py` / 旧版 `make_numpy.py` はこの配布版には入っていない。
> `automation/` は `batch_reconstruct.py` と `config.toml` だけ入っている。Iromiel Hyper SDK は入っていない）。

選んだ RAW だけ、29 バンドの配列を `.npy` にする。
npy は1枚 約160MB（uint16。float32 なら約320MB）あるので、RGB 化（`main.py` / `automation_rgb.py`）では作らず、RGB を見て選んだものだけをこれで作る。

```bash
python make_numpy/main.py        # 設定は make_numpy/settings.py
```

旧版の `make_numpy.py`（1ファイル版）も残してある。旧版は全部を再構成してから npy にする。
こちらは**日付フォルダごとに 再構成 → npy 化 を終えてから次の日付へ進む**（できる npy は同じ）。

---

## 1. ファイルの構成（1ファイル1関数）

| ファイル | 関数 | 何をするか |
|---|---|---|
| `main.py` | `main()` | 全体の流れ。日付フォルダごとに下の関数を順に呼び、最後に結果を表示する |
| `settings.py` | — | 設定（入力・出力・補正・動作） |
| `check_settings.py` | `check_settings()` | 設定の指定ミスがあれば止める。設定を表示する |
| `load_names.py` | `load_names(path)` | 名前ファイルから、npy にする RAW 名の一覧を読む |
| `find_raw.py` | `find_raw(names)` | RAW 名ごとに、どの日付・時間フォルダにあるかを探す |
| `select_targets.py` | `select_targets(found, calibration)` | 既存の npy・再構成結果・白板ROIを見て、作るもの／飛ばすものに振り分ける |
| `check_disk_space.py` | `check_disk_space(folder, n, mb)` | 1個 mb MB のファイルを n 個置く空きがあるか |
| `reconstruct_to_npy.py` | `reconstruct_to_npy(missing, calibration, dark)` | 再構成結果が無い RAW を SDK で復元し、PNG を作らずにそのまま npy にする（`DIRECT_NPY`） |
| `reconstruct_missing.py` | `reconstruct_missing(missing, calibration)` | 再構成結果が無い RAW を、Iromiel Hyper SDK で PNG に再構成する（`DIRECT_NPY = False` のとき） |
| `make_npy_files.py` | `make_npy_files(targets, dark)` | 再構成結果の PNG から1枚ずつ npy にする（失敗したら RETRY_COUNT 回やり直す。読み込みが READ_TIMEOUT_SEC 秒で終わらなければ止める） |
| `delete_reconstruct.py` | `delete_reconstruct(scenes)` | npy 化のために再構成した再構成データを、RAW名のフォルダごと消す |
| `make_bands.py` | `make_bands(scene, roi, dark)` | 再構成バンド（PNG）を読み、黒補正・白板補正をして npy にする配列を作る |
| `correct_bands.py` | `correct_bands(bands, roi, dark)` | 黒補正・白板補正（make_bands と reconstruct_to_npy の共通部分） |
| `npy_dtype.py` | `npy_dtype()` / `npy_mb()` | npy の型（補正なしなら uint16、補正するなら float32）と 1 枚の容量 |
| `save_npy.py` | `save_npy(array, name)` | `<OUTPUT_DIR>/<RAW名>.npy` に保存する |

## 2. main() の流れ

```
main()
 ├─ check_settings()          設定の確認・表示
 ├─ load_names()              npy にする RAW 名の一覧
 ├─ calibration.json          白板ROIの記録を読む（白板補正するときだけ）
 ├─ find_raw()                RAW 名 → どの日付・時間フォルダにあるか
 │
 ├─ for 日付フォルダ（10082026, 10092026, ...）:
 │    ├─ select_targets()      作成済み / 再構成結果が無い / 白板ROIが無い / 作る に振り分け
 │    ├─ check_disk_space()    npy の保存先と、再構成結果の保存先の空き（足りなければここで止める）
 │    ├─ reconstruct_missing() この日付の再構成結果が無いものを SDK で PNG に再構成（DIRECT_NPY = False のとき）
 │    │   └─ もう一度 select_targets()
 │    ├─ make_npy_files()      再構成結果（PNG）がある分の npy を作る
 │    │    └─ make_bands() → correct_bands() → save_npy()
 │    ├─ reconstruct_to_npy()  再構成結果が無い分を SDK で復元して、そのまま npy にする（DIRECT_NPY のとき）
 │    │    └─ コールバックで復元画像を受け取る → correct_bands() → save_npy()（別スレッド）
 │    └─ delete_reconstruct()  この日付で再構成して npy にできたものの再構成データを消す
 │                             （DIRECT_NPY = False で DELETE_RECONSTRUCT_AFTER_NPY のとき）
 │
 └─ 結果の表示                作れなかった名前を理由ごとに表示
```

1つの RAW 名の行き先:

```
RAW 名
 ├ RAW が見つからない        → 「RAW が見つからない名前」
 ├ 2か所以上にある           → 「複数のフォルダにある名前」（DATES で絞る）
 └ 1か所で見つかった
     ├ npy がもうある          → 既存スキップ（再構成結果を消してあっても）
     ├ 再構成結果のフォルダが一時的なエラーで読めない
     │                         → 飛ばす（「一時的なエラーで読めず、飛ばした名前」。再構成も npy 化もしない）
     ├ 再構成結果が無い        → SDK で復元して直接 npy にする（できなければ「失敗」）
     │                           DIRECT_NPY = False なら SDK で PNG に再構成（できなければ「再構成結果が無い名前」）
     ├ 白板ROIの記録が無い     → 「白板ROIが無い名前」
     └ そろっている            → npy を作る
```

### SDK から直接 npy にする（DIRECT_NPY）

SDK は 1 回の復元ごとに、コールバックで画像 30 枚をメモリのまま渡してくる
（0 枚目 = 撮影画像、1〜29 枚目 = band01〜29。どれも 1920×1440・16bit）。
この値は保存される band PNG と画素単位で同じなので（2026-11-07 に RAW 4 枚で、作成済みの npy と一致することを確認）、
PNG を書いて読み直す代わりに、これをそのまま npy にする。

* SDK には PNG・ENVI・log を保存させない。撮影画像の PNG だけは止められないので、
  `<RECONSTRUCT_ROOT>/_direct_npy_tmp/` に書かれたものを 1 枚ごとに消す。
* 1 枚の流れ: RAW を指定 → 撮影の合図 → 復元画像が届くまで待つ → 停止。届かなければ合図を送り直し
  （`config.toml` の `retrigger` / `retrigger_max`）、それでも失敗したら SDK を初期化し直して 1 回だけやり直す。
* npy の保存は別スレッドで行う（待ち行列は 1 件）。Box への書き込みを待つ間に、SDK が次の 1 枚を復元する。
  保存は一時ファイル → 名前の変更なので、途中で止めても書きかけの npy は残らない。
* 1 枚ごとの結果（成否・復元の秒数）は `<RECONSTRUCT_ROOT>/direct_npy_log.csv` に残る。
* 再構成結果（PNG）は作らないので、`DELETE_RECONSTRUCT_AFTER_NPY` や再構成結果の容量の確認は関係ない。
  もとからある再構成結果（PNG）は、今まで通り PNG から npy にする。

### npy の型（NPY_UINT16）

補正なし（黒補正・白板補正とも False）で `NPY_UINT16 = True` なら、npy を `uint16` で保存する。
再構成の値はもともと 16bit の整数なので劣化はなく、容量は `float32` の半分（1 枚 約 160MB）。
補正すると小数・負の値になるので、そのときは常に `float32`。

使う側では、計算する前に `np.load(path).astype(np.float32)` で変換する（`uint16` のまま引き算すると回り込む）。

### npy を作ったあとの再構成データの削除（DELETE_RECONSTRUCT_AFTER_NPY）

`True`（既定）なら、日付ごとに npy 化が終わったところで、**その実行で SDK を使って再構成し、npy にできた RAW** の
再構成データ（`<RECONSTRUCT_ROOT>/<日付>/<時間>/<RAW名>/` の中の band01〜29.png・ENVI・log など）を消す。

| | 消すか |
|---|---|
| その実行で再構成して、npy にできたもの | 消す |
| その実行で再構成したが、npy 化に失敗したもの | 残す（次の実行でやり直せるように） |
| もとからあった再構成データ（automation_rgb.py で作ったもの、Iromiel Hyper の出力など） | 残す（RGB化のやり直しに使うため） |
| RAW データ（`raw_data` の `.RAW`）、時間フォルダの `batch_log.csv` | 消さない |

* RAW名フォルダ形式（`<RAW名>/reconstruct/<RAW名>/`）になっていないものは、念のため消さない。
* npy 化に失敗して残った再構成データは、次の実行では「もとからあった」扱いになるので、npy にしたあとも残る。

### Box Drive の一時的なエラー（WinError 1237）

Box Drive の中で動かすと、フォルダの中身をクラウドから取れずに
`OSError: [WinError 1237] この操作を完了できませんでした。再実行してください。` になることがある
（再構成直後のフォルダで起きやすい。Box のログでは `Timeout fetching folder`）。

* このエラー（と 121・1460 のタイムアウト）のときは、1・2・4 秒待って最大 3 回やり直す（`hsi2rgb/fs_retry.py`）。
  ただし失敗までに 10 秒以上かかったとき（Box が中で 30 秒待ってから失敗を返したとき）は、やり直さずに飛ばす
  （すぐやり直しても同じで、壊れたフォルダ 1 つで数分待たされるだけなので）。
* やり直しても読めない再構成フォルダは、その実行では**飛ばす**。npy は作らず、再構成のやり直しもしない。
  最後に「Box Drive などの一時的なエラーで読めず、飛ばした名前」として表示する。
* Box Drive の同期が落ち着いてから（直らなければ Box Drive を終了→起動してから）もう一度実行すれば、続きから処理する。
* npy の中身を作る処理は変えていない。バンド PNG の一覧だけ、`glob` から `os.listdir` に変えた
  （`glob` は一覧の途中でエラーが起きても黙ってそこまでの分を返すので、バンドが欠けたまま npy になるおそれがあった）。
* RAW のフォルダ（`RAW_ROOT`）がやり直しても読めないときは、対象を決められないので最初に止まる。

Box Drive がファイルをダウンロードできない状態になると、エラーにならずに読み込みが何十分も戻らなくなる
（Box のログでは読み込みが 30 秒ごとにタイムアウトし、ダウンロードが完了しない）。

* バンドの読み込みが `READ_TIMEOUT_SEC` 秒で終わらなければ、その実行は止める
  （`--- 再構成バンドの読み込みが終わらないため、<日付> の途中で止めました ---`）。
  続けても1枚ごとに待たされるだけなので。Box Drive を終了→起動してから、もう一度実行する。
* 待つのをやめるのは読み込みだけ。npy の保存は読み込みが全部終わってから別に行うので、書きかけの npy はできない。
* 途中までしか読めなかった PNG はデコードでエラーになる（`画像を読み込めません`）ので、欠けたデータが npy になることもない。

### 再構成結果の容量が足りないとき

再構成結果は RAW 1枚あたり約 230〜250MB（png 29枚 約 65〜92MB ＋ ENVI 約 160MB）。
日付ごとに、再構成を始める前に「再構成する枚数 × `RECONSTRUCT_MB_PER_RAW`」の空きがあるかを確かめ、
足りなければその日付を始めずに止める（容量不足のまま SDK を動かすと、1枚ごとに失敗とやり直しを繰り返すため）。

```
--- 再構成結果の保存先の容量が足りないため、10092026 から先は処理していません ---
```

と出たら、npy 化が終わった日付の再構成結果（`<RECONSTRUCT_ROOT>/<日付>/`）を消して、もう一度実行する。
npy がもうある RAW は飛ばすので、止まった日付から続きを処理する。

* ENVI（.raw）は RGB化にも npy化にも使わない（`compare_with_app.py` の比較用）。
  `automation/config.toml` の `envi = false` にすると 1枚 約 70〜90MB になる。そのときは `RECONSTRUCT_MB_PER_RAW = 100`。
* 再構成結果を消すと、RGB化をやり直すときにもう一度再構成が必要になる。

## 3. 設定（settings.py）

### 入力・出力

| 設定 | 意味 |
|---|---|
| `RAW_ROOT` | `<RAW_ROOT>/<日付>/<時間>/<RAW名>.RAW`。日付フォルダの直下に RAW があれば、その日付フォルダを1つのまとまりとして扱う |
| `RECONSTRUCT_ROOT` | `<RECONSTRUCT_ROOT>/<日付>/<時間>/` に再構成結果。RAW と同じ日付・時間の場所を見る |
| `DATES` | 探す日付。例 `["10082026", "10092026"]`。空 `[]` なら `RAW_ROOT` の中を全部 |
| `CALIBRATION_JSON` | RGB 化のときの白板ROIの記録 `{"RAW名": [x0, y0, x1, y1]}` |
| `NAMES_FILE` | npy にする RAW 名。次のどれでもよい（下の表）。`None` なら `RAW_ROOT`（`DATES` の日付）にある RAW 全部 |
| `DARK_DIR` | 黒補正のダーク（band01..29.png のフォルダ） |
| `OUTPUT_DIR` | `<OUTPUT_DIR>/<RAW名>.npy`（日付・時間では分けない） |
| `NPY_UINT16` | 補正なしなら npy を `uint16` で保存する（上の「npy の型」を参照）。`False` なら `float32` |

名前ファイルの形式:

| 形式 | 例 | 対象 |
|---|---|---|
| meta_data.json | `[{"image_id": "00800725", "metadata": {...}, "calibration": [...]}, ...]` | 全件の `image_id`（`metadata` と `calibration` は使わない） |
| keep / reject の JSON | `{"00480902": "keep", "00480903": "reject"}` | keep のものだけ |
| リストの JSON | `["00480902", "00480903"]` | 書いたもの全部 |
| テキスト | 1行1名 | 書いたもの全部 |

`00480902.RAW` のように拡張子付きで書いても RAW 名として扱う。

再構成結果のフォルダは次のどちらの形でも読める。

```
<RECONSTRUCT_ROOT>/<日付>/<時間>/<RAW名>/reconstruct/<RAW名>/band01..29.png   automation の出力
<RECONSTRUCT_ROOT>/<日付>/<時間>/reconstruct/<TS>/band01..29.png            Iromiel Hyper の出力（RAW と名前順で対応）
```

### 補正（RGB 化のときと同じにする）

| 黒補正 | 白板補正 | npy の中身 | 必要なもの |
|---|---|---|---|
| False | True | 再構成の値を白板で割った反射率 | `CALIBRATION_JSON` |
| True | True | ダークを引いてから白板で割った反射率 | `CALIBRATION_JSON`、`DARK_DIR` |
| True | False | 再構成の値 − ダーク | `DARK_DIR` |
| False | False | 再構成の png の値そのもの | なし |

`WHITE_BOARD_REFLECTANCE` は白板の反射率。白板補正後、白板の場所がこの値（0.9）になる。

```
npy の値 = 0.9 × (再構成の値 − ダーク) ÷ 白板ROI内の平均（ダークを引いたあと、バンドごと）
```

* `calibration.json` には白板の位置しか残っていないので、補正の設定が RGB 化と食い違っていても気づけない。
* 補正の設定を変えて作り直すときは `OUTPUT_DIR` を分ける（同じ名前の npy が「作成済み」として飛ばされるため）。

### 動作

| 設定 | 意味 |
|---|---|
| `OVERWRITE` | 既にある npy も作り直すか |
| `RETRY_COUNT` / `RETRY_WAIT_SEC` | 1枚が失敗したときのやり直し回数・待ち時間 |
| `READ_TIMEOUT_SEC` | 1枚の再構成バンドを読み終わるまでの上限 [秒]（既定 600）。超えたら Box Drive が応答していないとみなし、その実行を止める |
| `RECONSTRUCT_MISSING` | 再構成結果が無ければ SDK で再構成する |
| `DIRECT_NPY` | 再構成結果が無いものは、PNG を作らずに SDK から直接 npy にする（上の「SDK から直接 npy にする」を参照）。`False` なら PNG に再構成してから npy にする |
| `AUTOMATION_DIR` | `batch_reconstruct.py` と `config.toml`（再構成の設定）の場所 |
| `RECONSTRUCT_MB_PER_RAW` | 再構成結果 1枚の容量の目安 [MB]。空きの確認に使う（ENVI を保存するなら 260、しないなら 100。`DIRECT_NPY` では使わない） |
| `DELETE_RECONSTRUCT_AFTER_NPY` | npy 化のために再構成した再構成データを、npy を作ったら消すか（上の「削除」を参照） |

`RECONSTRUCT_MISSING` の注意:

* GPU のある PC でだけ使える。GPU の無い PC では `False` にする。
* 再構成は RAW と同じ日付・時間のフォルダ（`<RECONSTRUCT_ROOT>/<日付>/<時間>/<RAW名>/`）に作る。
  Iromiel Hyper 形式のフォルダには追加しない。
* 白板補正するなら、白板ROIの記録がある（RGB 化済みの）RAW だけ再構成する。
* 再構成の設定は `automation/config.toml`（`limit` と `overwrite` は使わない）。
